# 01 · Turso 数据库表结构设计说明

> 对应文件：`db/schema.sql`（建表）+ `db/seed.sql`（演示数据，可选执行）

## 一、四张表总览

| 表名 | 职责 | 关键设计 |
|---|---|---|
| `users` | 用户信息 + 身材画像 | 三围/肤色/脸型/风格偏好，为"推荐符合硬件条件"服务 |
| `wardrobe_items` | 虚拟衣橱单品 | 图片只存 URL；`warmth_level`/`formality` 两个数值字段驱动情景引擎 |
| `outfit_history` | 穿搭历史 | 单品 ID 存 JSON 数组；日期倒序索引支撑"本月搭配"统计 |
| `daily_recommendations` | 每日推荐缓存 | **UNIQUE(user_id, recommend_date, occasion)**，刷新不烧 AI 额度 |

## 二、核心设计决策

### 1. 排重为什么用冗余字段，而不是每次扫历史？

排重需求是"避开最近穿过的款式"（高频、每次推荐都要执行）。两种方案：

- ❌ 每次推荐时 `SELECT ... FROM outfit_history ORDER BY worn_date DESC` 再解析 JSON 反查单品 → 多一次跨表查询 + JSON 解析开销
- ✅ 单品表直接维护 `last_worn_at` + `wear_count`，记录穿搭时一个事务顺手更新 → 推荐时只查衣橱一张表

`outfit_history.item_ids` 仍保留 JSON，作为回溯与"近 2 天穿过集合"的第二数据源（`api/recommend.ts` 中两者结合）。

### 2. 厚度与正式度：把"感觉"翻译成数字

天气决定穿多厚，场合决定穿多正式——这是情景引擎的地基：

| 字段 | 取值 | 含义 |
|---|---|---|
| `warmth_level` | 1~5 | 1=吊带/凉鞋（盛夏）→ 5=羽绒/雪地靴（寒冬） |
| `formality` | 1~5 | 1=居家 → 2=日常 → 3=通勤 → 4=约会 → 5=面试/正装 |

引擎按体感温度映射目标厚度区间（≥26°C → 1~2；18~25 → 2~3；10~17 → 3~4；<10 → 4~5），
按场合映射目标正式度，匹配±1 档内挑选，多级放宽兜底，保证衣橱再小也能出结果。

### 3. 每日推荐缓存的省钱结构

```
UNIQUE(user_id, recommend_date, occasion)
```

- 前端刷新 → 直接命中缓存，`status` 置为 `shown`
- 点"就穿这套" → `is_accepted=1`，同时 POST /api/history 落历史
- 点"换一套" → `refresh=1` 重新生成，UPSERT 覆盖，`swap_count+1`（顺带观察选择困难度）
- `alt_outfits_json` 预留：第三阶段一次生成 2~3 套备选，"换一套"零成本轮换

### 4. JSON 文本列的使用边界

SQLite 无原生 JSON 类型。凡"整体读写、不按内部字段查询"的数据用 TEXT+JSON：
风格偏好、天气快照、推荐明细、备选方案。
凡需要 WHERE/ORDER 的数据必须拆成独立列（如 `category`、`last_worn_at`）。

## 三、索引清单

| 索引 | 支撑查询 |
|---|---|
| `idx_items_user_category` | 衣橱页按分类浏览 |
| `idx_items_last_worn` | 排重 + 首页"未穿单品"统计 |
| `idx_history_user_date` | 历史时间线 + 本月搭配数 |
| `idx_rec_user_date` | 推荐缓存命中 |

## 四、建库三步（本地即可执行）

```bash
# 1. 创建数据库（turso login 后）
turso db create dapei

# 2. 建表：执行 schema
turso db shell dapei < db/schema.sql

# 3. 拿凭证配置环境变量
turso db show dapei --url        # → TURSO_URL
turso db tokens create dapei     # → TURSO_AUTH_TOKEN
```

> 可选：`turso db shell dapei < db/seed.sql` 写入演示用户 + 三件单品 + 昨日历史，
> 可立即验证排重（今天推荐的必须避开这三件）。
